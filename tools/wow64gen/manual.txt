# wow64gen deep-marshal list — Nt* syscalls whose `ptr` args point at a struct
# whose 32-bit and 64-bit layouts DIFFER, so ABI-level arg widening is not
# enough. wow64gen emits these as WOW64_NEEDS_MANUAL stubs; implement each by
# hand in wow64_manual.c (translate the 32-bit struct into a 64-bit one on the
# stack, call the real Nt*, copy any output back). One name per line; # starts
# a comment. Re-run wow64gen after editing.
#
# Seeded with the highest-frequency structural offenders. This is intentionally
# INCOMPLETE — add names as boot coverage exercises more of the surface. When
# unsure whether a syscall belongs here, list it: a loud manual stub is always
# safer than a silently-wrong auto thunk.
#
# Categories:
# --- OBJECT_ATTRIBUTES takers (ObjectName is a 32-bit UNICODE_STRING* whose
#     Buffer is a 32-bit ptr; the 64-bit struct is wider) ---
# --- IO_STATUS_BLOCK.Information is ULONG_PTR (4 vs 8 bytes) + these carry
#     OBJECT_ATTRIBUTES and/or overlapped state ---
# --- context / LARGE_INTEGER-by-value / arrays of pointers ---

# --- M10: the IO_STATUS_BLOCK family ---
# Every one of these takes an IO_STATUS_BLOCK, whose `ULONG_PTR Information` is
# 4 bytes on i386 and 8 on the host: the guest's struct is 8 bytes, the host
# kernel writes 16. Auto-thunking them (which is what happened before M10) both
# overflows the guest struct by 8 bytes AND reads Information from the wrong
# offset. The first six + NtQueryDirectoryFile are implemented in wow64_manual.c
# (Doom needs ReadFile); the rest are listed so they fail LOUD instead of
# silently corrupting the guest — implement on demand.
