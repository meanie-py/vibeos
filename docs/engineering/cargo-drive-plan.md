# Cargo drives the build: moving fully-Rust modules off cmake

**Opened 2026-10-12.** A module whose C is all translated should be built and linked by
Rust tooling, with cargo calling the C compiler where C is genuinely left, not by cmake
wrapping a placeholder `.c`. This revives the June cmake-off program
([archive/cargo-drive-cmake-off-roadmap.md](archive/cargo-drive-cmake-off-roadmap.md),
whose kernel/spine results are summarised in [build-system.md](build-system.md)) and
extends it from the boot spine to every fully-Rust module.

## Where we are (measured 2026-10-12, amd64 build graph)

- **230 of 310 cmake targets in Rust-touched directories compile no real C**: only a
  placeholder `rust_cohab_stub.c`, a varargs shim, generated spec stubs or resources.
- **Only 38 link through cargo** (`add_cargo_module` + `reactos-link`): the kernel, HAL
  pieces, the boot spine, some drivers, cabinet, mlang. **224 fully-Rust modules are
  still linked by cmake**, around the placeholder TU.
- What cmake still does for those 224: import libs (201), CD placement (200), resources
  (189), the placeholder stub (198), spec2def exports (79), PCH (75), C static libs
  (~110 modules link one: `uuid` 87 TUs of GUIDs, `wine` 9, `conutils` 2, a few more),
  delay imports (13), registry INFs (10), IDL (5).

## The tools

- **`tools/cargo_orchestrate.py`** builds cells with no cmake configure and no ninja.
  Its `--verify` builds every cell twice, replaying cmake's commands and then forced
  cmake-off, and requires the results to be byte-identical bar the PE timestamp.
  It had silently rotted since June (nothing ran it). Two fixes, 2026-10-12:
  it re-enters the canonical `/tmp/vibeos` mount itself (the replayed `widl` command
  `cd`s there), and it runs ONE cargo per cell (a single `cargo build -p a -p b ...`
  unifies features, and the kernel's `KeBugCheckEx` panic path leaked into csrss, smss
  and csrsrv). After: the 35 cells of `--all` are byte-identical on amd64.
- **`tools/cargo_cell_gen.py`** generates a module's `<m>-cargo` cell from the link cmake
  actually runs (`build-<arch>/build.ninja`: entry, subsystem, image base, libraries,
  `.def`, resources, on all three arches), and rewrites its `CMakeLists.txt` to
  `add_cargo_module`. It refuses any shape it does not model. `--survey` lists every
  placeholder-stub module with its verdict; `--save-baseline` / `--check` compare.
- **`tools/pe_equiv.py`** is the acceptance check. A cargo link cannot be byte-identical
  to the cmake one (lld sees the objects in another order), so it compares what the
  loader and callers see: headers, every export, every import (normal and delay), every
  resource by content hash, section names and flags.

## The ladder

1. **Repair and gate the orchestrator. Repaired 2026-10-12:** `--all --verify` is
   byte-identical on every cell, all three arches (amd64 35, i386 35, arm64 36). Owed:
   run it somewhere automatic so it cannot rot again. It takes about 45 minutes for all
   arches, too slow for `check`; `--spine` on amd64 is about 2.
2. **Generate cells, in waves, each proven by `pe_equiv` ×3 then smoke ×3.**
   - **Pilot, 2026-10-12: 15 Wave I modules** (bootok, conime, dllhost, expand, fmifs,
     indicdll, kbswitch, regsvr32, rundll32, runonce, subst, umandlg, utilman, winmine,
     wuauserv). All 45 module×arch pairs equivalent; smoke ×3 green. `cargo_cell_gen
     --check` accepts exactly three named differences, and reports each:
     - **panic_common imports added** (`DbgPrint`, `NtTerminateProcess`,
       `RtlWalkFrameChain`, mem functions): the cell's empty bin carries the same
       `panic_common` handler the body defines, and cmake's link had garbage-collected
       the body's copy.
     - **i386: mem/str intrinsics no longer imported** from msvcrt: i386 cells build
       `core` with `compiler-builtins-mem`, so they resolve statically. userinit and lsass
       have linked that way since June.
     - **`__chkstk` imported on amd64/arm64**: the engine forces frame pointers on the
       body build (stack walks need them) where cmake did not, which can push a frame
       over the probe threshold. ntdll exports it; kernel32 forwards.
     Anything else, and every removed import or resource, fails the check.
   - **Wave 2, 2026-10-12: 94 modules**, every one the generator then accepted (the
     list is the `add_cargo_module(... generated by tools/cargo_cell_gen.py)` blocks).
     All 282 module×arch pairs equivalent; smoke ×3 green. Two more accepted
     differences: panic_common's mem functions can come from ntdll (wlnotify imports
     no msvcrt), and `DEAD_IMPORTS` lists a removal checked by hand as dead code
     (sndvol32 arm64 drops `FormatMessageW`, reached only from a varargs trampoline
     nothing calls). Applying it taught the generator to refuse five shapes it had been
     reading from the amd64 link alone. These modules are owed in a later wave:
     - kernel-mode `native:` DLLs (bmfd, ftfd, ndis, watchdog): need `KernelDll`.
     - link inputs that differ by arch (acgenral's amd64-only `msys2.c`, opengl32's
       i386 asm trampolines).
     - `rust_staticlib_variant` extras (calc, taskmgr, wordpad: the i386 body's
       `+sse,+sse2`, which `pe_equiv` cannot see).
     - a different CD destination per arch (winprint's `prtprocs/<arch>`).
     - a `SOURCE` list another target also builds (gdi32_vista_static).

     **The first submission was rejected** (kmtest `MmMdl` 720 -> 714 on amd64, 3 of
     3: one fewer 32 MB block of free memory). pe_equiv had passed, because size is
     not in the contract. Every cell's empty bin carried `panic_common`, and that
     loaded all of `core`: rustc roots each dependency's `#[no_mangle]` symbol in an
     executable link (panic_common's `_Unwind_Resume` fallback is one), and the
     precompiled `core` for the builtin windows-gnu triples is one non-COMDAT
     section, which lld's COFF gc never discards. w32time.dll went from 10 KB of
     code to 147 KB; the wave added 18.5 MB on amd64, and five pilot modules
     (bootok, expand, indicdll, subst, wuauserv) already carried it on master. cmake
     never paid this: it pulled the body's handler lazily, only when something could
     panic. The fix:
     - **`panic-lean`**, a handler that references nothing in `core`, for every arch
       on which the cmake-built module carried no handler (no `RtlWalkFrameChain`
       import). The generator decides per arch; `--reshell DIR` redoes it for an
       existing cell from its baseline.
     - **`--check` guards size**: the mapped image may not grow more than 16 KB.
       amd64 is now +21 KB across the whole wave, arm64 3 KB smaller than cmake.
     - **i386 cells on the user target, 2026-10-14.** An i386 cell built its own
       `core` (nightly build-std on the kernel json) beside the body's
       i686-pc-windows-gnu one, so a cell that kept `panic_common` linked a second
       copy of `core::fmt`, 70-78 KB each. Every i386 user-mode cell (KIND win32dll /
       win32exe, 160 of them, ntdll included) now links the builtin
       `i686-pc-windows-gnu` on stable, like amd64; only the kernel kinds keep the
       softfloat json and nightly. Across all 285 i386 cargo-linked PEs the mapped
       size fell 6.9 MB. What the triple brings, and how it is met:
       - `rsbegin.o` (linked even with `link-self-contained=no`) registers the
         image's `.eh_frame` with libgcc. Nothing unwinds in a panic=abort image
         with no libgcc, so reactos-link gives `__register_frame_info` /
         `__deregister_frame_info` no-op bodies. Its `.ctors`/`.dtors` entry each get
         a 4-byte section (lld's MinGW writer makes those sections, so `/MERGE`
         cannot fold them); `--check` accepts exactly those two on i386.
       - The spec's `--large-address-aware` is cleared (`-Xlink=-largeaddressaware:no`).
       - mem/str intrinsics are imported from msvcrt or ntdll again, as cmake's links
         did; the build-std `compiler-builtins-mem` copies are gone.
       - The cell keeps the bodies' `-sse,-sse2`, the combination rustc is phasing
         out; `tools/scan_i386_sse_abi.py` counts gcc.cmake as a site.
   - **Wave 3, 2026-10-13: 22 modules** the generator learned to accept: chcp,
     chkdsk, cmd_help, console, dbgprint, extrac32, fltlib, hid, imm32, logon, mmc,
     mode, more, msiexec, progman, reg, regedit, route, taskkill, tree, wmic, xcopy.
     What it learned:
     - **The body is the variant the module links**, not the one named
       `<target>_rust` (cmd_help_rust for help.exe): the `lib<name>.a` in the link
       edge names it. A variant another target still links stays in the CMakeLists.
     - **Compile settings move to the OBJECT libraries.**
       `target_compile_definitions` / `_include_directories` / `_compile_options` /
       `set_wine_module[_FIXME]` on the target are re-aimed at `<m>_res` and
       `<m>_shims`, so the rc and C compile as cmake compiled them.
       `set_target_properties` that only sets SUFFIX / OUTPUT_NAME / PREFIX is
       dropped: the cell takes the output name from the link edge.
     - **Library order follows cmake's.** A user module links its body before
       `uuid`/`wine`; the engine put cmake-built libs before the Rust (ntdll and the
       kernel need that), so regedit's duplicate CLSIDs resolved to uuid's and
       link_guard refused. `static_libs_after_body` takes what cmake linked after.
     - **A link edge is found by its config suffix**: `cmd_\S*` had matched
       cmd_help's edge for cmd.exe. Waves 1 and 2 were not affected: a wrong edge
       saves the wrong module as the baseline and pe_equiv would have failed.
     - `--save-baseline` writes `targets.json` (target -> output), because a target
       is not always its file name.
   - **Not this generator's job**: 34 refusals are kernel drivers and kernel static
     libraries (the USB stack, file systems, storport, ks, …) that build their Rust
     with their own custom command; they are the driver rung (`KernelDll` and
     driver kinds).
   - **The 95 keyboard layouts: one FAMILY cell, 2026-10-13.** They were one
     `foreach` over a shared `kbdlayouts-rust` body, so instead of 95 generated
     cells, `sdk/lib/rust/kbdlayouts-cargo` is one package with a `[[bin]]` per
     layout, all over the same empty `main.rs`. What it took:
     - **`Linker::for_bin(name)`** in reactos-link: every argument goes out as
       `rustc-link-arg-bin=<name>=…`, and intermediates (`.res`, `.def`, objects) go
       in per-bin dirs, so one build.rs makes 95 separate link lines. The body's
       nested cargo build, the host spec2def and the parsed `compile_commands.json`
       are memoized per build-script process, so the body compiles once.
     - **`add_cargo_module(... BINS <names>)`**: one `cargo build --bins`, then a copy
       and the kind's post-link and a cd entry per output. Configure fails if BINS
       and the crate's `[[bin]]` list differ: a layout missing from either would
       silently not ship. The 95 `.rc`s compile in one OBJECT library,
       `kbdlayouts_res`.
     - **`link_args()`** for what no ModuleKind models: cmake's `/MERGE`s of every
       section into one executable `.data`. A layout imports nothing (win32k reads
       it in kernel context), so the bin's panic handler is a `__fastfail` trap. It
       is a rooted lang item, linked even from an rlib nothing references, so its
       amd64/arm64 unwind entry needs one merge cmake's list lacks, `.pdata`.
     - Result: `--check` EQUIVALENT on all 285 module/arch pairs with nothing
       accepted. Each DLL is the same size or one or two 512-byte file-alignment
       blocks larger (the handler's few bytes). Cargo links all 95 in about a
       minute per arch.
   - **Wave 4, 2026-10-14: 18 modules with delay imports or generated C.** apphelp,
     appwiz, cmd, comctl32, control, iexplore, inetcpl, netsh, spoolsv, wscript (delay
     imports); eventlog, netlogon, rpcss, schedsvc, seclogon, srvsvc, winspool (widl
     RPC stubs) and winhlp32 (a flex scanner). What it took:
     - **`Linker::delay_import_lib()`** runs `sdk/tools/gen-delaylib.py` on the same
       `spec2def --implib` .def as `import_lib`, as cmake does, and
       `add_cargo_module(... DELAY_IMPORTS)` adds cmake's `native-pefixup
       --delayimport`. **Import order is cmake's**, one list for both kinds:
       gen-delaylib puts a DLL's thunks in one object, so pulling one defines every
       `__imp_` of that DLL. inetcpl delay-imports shell32 (which also exports
       `StrChrW`) and imports shlwapi; delayed-first binds `StrChrW` to shell32, and
       the other order defined it twice and crashed lld in `IdataContents::create`.
     - **Generated C** (`*_s.c`, `macro.lex.yy.c`) is a `<m>_shims` source named
       build-dir relative; cmake still generates it, `c_from_compile_db` replays the
       compile. **The shims library links what the target linked**: libmsvcrt's
       `INTERFACE _DLL __USE_CRTIMP` reached the target's compiles that way, and
       without it the scanner's `stdin` was not dllimport (`_iob` undefined).
     - **The import lib's spec is the one the build used**, read from
       `build.ninja`'s `spec2def --implib` command, not the first `spec2def()` in a
       CMakeLists. uxtheme has two (`uxtheme_vista.spec` under an option), and
       comctl32's delay lib grew twelve uxtheme imports. A regular import lib hides
       the mistake, so dxdiag (ddraw, dsound) and shsvcs (uxtheme) had it too and are
       repointed; their imports do not change.
     - **Several CD destinations** (comctl32's two winsxs assemblies): `DESTINATION`
       is a list, the winsxs copies go in the cabinet like system32's, and the
       generator checks each arch's `livecd.<config>.lst` holds exactly the
       destinations the CMakeLists names, which is what refuses winprint's one
       prtprocs dir per arch.

     i386 `ENV "RUSTFLAGS=+sse,+sse2"` is modelled in its one exact shape (`_body_env`:

     becomes `rust_build_rustflags` on that arch. Per-arch CD dirs (winprint's
     `prtprocs/<arch>`) become one `<M>_DESTINATION` variable. ftp was a new

## How a wave goes (the default for every new module)

**A fully-Rust module is a cargo cell.** After `rustconv port flip` and the build that
follows it, run

    python3 tools/cargo_cell_gen.py --convert <target> [<target> ...]

It baselines the cmake-built PEs that build left in `build-<arch>`, models every target
before writing anything (one refusal writes nothing), applies, regenerates each arch's
graph, builds only the new cells (`ninja <targets>` under the canonical mount) and runs
`--check`: minutes, not the three extra full builds the manual wave cost. `port flip`
prints the command. `vibeos-cli check` enforces it: `scan_cmake_linked_rust` (deferred,
it reads `build-amd64/build.ninja`) lists every module still linked by cmake around a
placeholder stub, as `(convertible)` or `(refused)`; the baseline holds only refused ones,
so a newly flipped module or a refusal the generator has learned to handle is a NEW
finding until it is converted. Teaching the generator a refused shape shrinks the
baseline.

`--convert` ends by regenerating what a build with no cmake reads: the cell and media
manifests and the shared C libraries' recipes. They are deliberately NOT gated: they are
derived from the build graph while cmake still owns cells and CD placement, so a merge
that adds a cell is stale only once the merged tree is configured, inside the gate itself
(a lint, `scan_cargo_manifests`, did exactly that and bounced a cold gate for a generated
file; retired the same day). Instead every consumer reads the live graph when there is
one (`cell_manifest.current`, `media_manifest.current`), and the committed copies serve a
build with no graph. `cell_manifest.py --check` / `media_manifest.py --check` report drift
as added/removed entries.

The manual steps, still there for a wave: build ×3, `--survey`, `--save-baseline DIR`,
`--apply`, build ×3, `--check DIR`.

A change that should not move a single mapped byte (a library now built by another
tool from the same source) gets the stricter proof: snapshot every cargo PE first, then
`python3 tools/pe_equiv.py --code OLD NEW` on each. lld is deterministic, so only DWARF
and `.buildid` may differ. `VIBEOS_LINK_MAP=1` on a build writes `build-<arch>/<cell>.map`,
which names every archive member each link pulled.

The generator reads the link from `build-<arch>/build.ninja`, so it must run on a graph
cmake configured from the ORIGINAL CMakeLists. To redo a module after `--apply`, put its
files aside (`git stash push -u -m ...`) and regenerate the graph (`ninja build.ninja`
under `tools/canon-run.sh`, per arch) before applying again.

## Rules this program has already earned

- **One cargo per cell.** Never `-p a -p b` across cells with different features.
- **Run inside the canonical mount** (`tools/canon-run.sh`), like every other build.
- **Nothing lands without `pe_equiv` ×3 against the cmake-built baseline, then smoke ×3.**
- **A dropped resource is a regression.** Earlier cutovers dropped "version-only" `.rc`s;
  the generator keeps every resource, and `pe_equiv` hashes them.
- **C that is left keeps its exact compile.** It goes in an OBJECT library cmake still
  configures, and the cell replays that command (`c_from_compile_db`), never a re-derived
  flag set.
- **Read every arch's link, not amd64's.** An `if(ARCH ...)` in a CMakeLists is
  invisible in one graph; the generator compares inputs, libraries, imports and
  destinations across all three and refuses on any difference it does not model.
- **`<m>_c` belongs to `c_oracle.cmake`** (the pre-flip C, built on request). The
  generated OBJECT library for leftover C is `<m>_shims`.
- **Equivalent is not enough: size is checked too.** A cell must not map code
  cmake's link did not; a whole `core` rode into 94 modules past pe_equiv.
- **The `# x.c  # replaced by Rust (...)` lines survive the rewrite.** `cohab_census` and
  the coverage tools read them; the generator carries every one into the new block.
