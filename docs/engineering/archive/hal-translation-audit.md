# HAL C→Rust Translation Audit

Last updated 2026-06-21. Companion to [`ntoskrnl-translation-audit.md`](ntoskrnl-translation-audit.md).

> **Ground-truth re-verified 2026-06-21** against `hal/halx86/*.cmake` + `hal/halarm64/CMakeLists.txt` + the `hal-rust` crate. HAL is complete; the two ACPI files previously flagged as remaining C (`acpi/halacpi.c`, `acpi/halpnpdd.c`) are flipped to Rust (`halacpi.rs` / `halpnpdd.rs`, both commented out in `acpi.cmake`). Only `.S` asm + autogenerated placeholders remain non-Rust. arm64 hal.dll is cargo-driven (`add_cargo_kernel_dll`).

**Translation: ~97% (methodology).** Of the substantive HAL driver code (every `.c` hardware driver across `halx86/{generic,legacy,pic,acpi,apic}` + the arm64 stub HAL), 100% is now Rust — **42 `# replaced by Rust` cohab markers** across the five x86 flavor cmakes (generic 16, legacy 9, pic 7, acpi 4, apic 6), and the arm64 `halstubs.c` is retired in favor of `arm64/halstubs.rs`. The residual non-Rust (~3% by LOC) is **not vibeos-authored C**: 5 shared `.S` asm files (~631 LOC, sit on the NT-ABI struct-offset boundary) + 3 one-line autogenerated `lib_hal_*_empty.c` placeholders + 2 i386-only `setjmp`/`longjmp` V86 BIOS trampolines (`bios.c`/`x86bios.c`, S-class by design). The `hal-rust` crate is **~21.6K LOC across 53 `.rs` files** (x86 driver layer 46 files / ~20.2K LOC; arm64 stub layer 3 files / ~1.27K LOC; plus the module roots). Note: the freeldr `lib/strsafe_shim.c` variadic shim is a FreeLDR glue file, **not** part of the HAL build.

## Status — 2026-06-21

**HAL translation COMPLETE — x86 AND arm64.** Every substantive HAL hardware driver is Rust. All 3 arches smoke green. The *only* non-Rust left compiling is shared `.S` assembly and autogenerated placeholders (see below); nothing of ours remains as C.

What's actually still non-Rust in the build (and why none of it is our translatable residue):
- **5 `.S` asm files** — `generic/systimer.S`, `generic/trap.S`, `pic/pic.S`, `apic/apictrap.S`, `apic/tsccal.S` (~631 LOC). Stays asm. NOTE: these *do* have a transitive dependency on C — they `#include <ks386.inc>`/`<ksamd64.inc>`, which the `geninc` host tool generates from `sdk/include/asm/genincdata.c` (which `#include`s the NT ABI headers ntdef/ntifs/ntndk/windbgkd/kddll). But that is a dependency on **NT struct field-offset definitions (headers)**, not a compiled C TU — and it's the *same* struct layout `ntkrnl-sys` bindgen already mirrors into Rust. Porting the asm to `global_asm!` would not sever it (Rust asm still needs the offsets via `offset_of!`). The asm-macro framework (`asm.inc`/`asmmacro.S`) and the gen-inc tooling are **pre-existing ReactOS** (Timo Kreuzer / reactos.org), not vibeos-authored. So this is the ABI boundary, not residue.
- **3 autogenerated `lib_hal_{generic,legacy,acpi}_empty.c`** — one-line `/* placeholder */` files that exist only to give the `lib_hal_*` OBJECT-lib targets a source. Eliminable via an `add_hal(COMPONENTS …)` cmake refactor; zero functional value.
- `legacy/bus/pcibus.c` — **RESOLVED, fully Rust on both arches** (i386 + amd64). pcibus.c is commented out of both `legacy.cmake` and `acpi.cmake`; only `pcibus.rs` is linked. The amd64 "BUGCHECK 0x1E in MM" that earlier blocked the swap was fixed in commit `a0650113864`: `pcibus.rs` hardcoded `HIGH_LEVEL = 31` (the i386 value), but amd64 KIRQL maps to CR8 (4 valid bits) so `mov cr8, 0x1F` set a reserved bit → #GP, mis-attributed by exception dispatch to `MiAcquireExpansionLock` (which is *why* it looked like an MM bug). Fix = per-arch `HIGH_LEVEL` (31 i386 / 15 amd64). Verified cold-build + smoke green ×3.
- `minihal/halinit.c` — **disabled, fully Rust** (kept on disk per the cohab convention; 0 refs in all 3 build.ninja). The 7 mini-HAL init stubs are in `sdk/lib/rust/hal-rust/src/x86/minihal_stubs.rs` (`cfg(all(target_arch="x86", feature="minihal"))`); the real impls in `pic_halinit.rs` etc. are gated `cfg(not(feature="minihal"))` so the stubs win in `libhal_rust_mini.a` without `--allow-multiple-definition`.
- `generic/bios.c` + `generic/v86.S` + `legacy/pci_classes.c` + `legacy/pci_vendors.c` — **removed from the tree** (no longer on disk). bios.c/v86.S were the pre-Vista V86 INT10 path; the PCI ID tables are now `pcidata.rs` (`include_bytes!`). `generic/x86bios.c` → `x86bios.rs`.

Whole `apic/`, `acpi/` (incl. halacpi + halpnpdd), `pic/`, `generic/`, `legacy/` (incl. pcibus on **both** arches), and **arm64 `halstubs`** subtrees are Rust.

### Strategy in force (updated 2026-06-21)

1. **arm64 HAL is now Rust too.** `hal/halarm64/generic/halstubs.c` (1,007 LOC) is **retired** (0 refs in build-arm64/build.ninja, kept on disk) → `sdk/lib/rust/hal-rust/src/arm64/halstubs.rs` (1,055 LOC) + `arm64/clock.rs` (206 LOC), `#[cfg(target_arch="aarch64")] mod arm64`. hal.dll (arm64) is cargo-driven (`add_cargo_kernel_dll(hal hal-cargo hal.dll BODY_CRATE hal-rust …)`, verified in `hal/halarm64/CMakeLists.txt`). It is still *stubs* (Rust ones), and a real ARM64 HAL (GIC + Generic Timer + PSCI + SBBR ACPI) remains a separate greenfield project — but the C→Rust translation of the existing stub HAL is done, and arm64 boots on it.
2. **All real hardware-driver Rust HAL work is x86 (i386 + amd64).** That's where ~20.2K LOC of real driver Rust lives (`src/x86/`, 46 files); arm64 is the thin ~1.27K-LOC stub layer above.
3. **Crate is single `hal-rust` cdylib-flavored staticlib** producing `libhal_rust.a` (and `libhal_rust_mini.a` via `--features minihal`), linked into the cmake-built `hal.dll` modules. Cohabitation, not full DLL takeover.
4. **Portable submodules + arch backends** — design intent preserved. In practice, current Rust is mostly under `src/x86/` with cfg-gated arch splits inside files; haven't needed to factor out portable trait surface yet.

```
├── Cargo.toml                  # staticlib, [features] minihal = []
└── src/

    ├── x86/                    # 46 .rs files, ~20.2K LOC (i386 + amd64 driver layer)

```

Total: **~21.6K LOC across 53 `.rs` files.** The real driver code lives under `src/x86/`; the other module dirs are one-line re-export roots, and arm64 is the thin stub layer.

CMake links `libhal_rust.a` into each `add_hal()` target and `libhal_rust_mini.a` into the freeldr-side mini_hal consumers. C files retired from the build are commented out in the per-flavor `.cmake` files (`generic.cmake`, `legacy.cmake`, `pic.cmake`, `acpi.cmake`, `apic.cmake`) with a `# replaced by Rust (path)` line so the mapping is greppable.

## Stage 0 — bindgen substrate (DONE)

`ntkrnl-sys::hal_ddk` provides the HAL-private bindgen layer for all 3 arches (only x86 is consumed today). Includes:

- HAL internal headers (`halhw.h`, `halp.h`, `haldma.h`, `bus.h`, `ioapic.h`)

## Stage 3 — DLL boundary (current state: incremental cohabitation)

The original plan was a hard cutover: `hal-rust` becomes a cdylib and `add_hal()` consumes it directly. In practice we've taken the **incremental cohabitation** path:

- `libhal_rust.a` is a staticlib that ntoskrnl HAL flavors link in.
- C files retired one at a time in the per-flavor `.cmake`; Rust takes over without changing the DLL build target.
- `--allow-multiple-definition` linker flag allows side-by-side C+Rust during the swap-in phase; only one definition wins (lld first-match), and the comment-out commits cleanly when the smoke confirms.

This trades the "clean cargo-only HAL link" milestone for ability to swap files individually with smoke as the gate. Cleaner in practice; each swap is a small reversible PR.

| Cohort | Count |
|---|---:|

| `-arch=x86_64` | 2 |
| `-arch=arm64` | 2 |

Internal `Halp*` functions in `include/halp.h`: ~144 declarations. The cohabitation pattern requires these signatures to stay stable through the translation window — both C and Rust have to agree exactly on calling convention, return type, and parameter layout. Per-arch ABI mismatches caused real bugs (memory `feedback_hal_extern_system_vs_c.md`); current best practice is to declare HAL Rust functions with `extern "system"` for NTAPI symbols, `extern "fastcall"` for FASTCALL, and bare `extern "C"` for pure cdecl, matching the C header verbatim.

## What this audit doesn't measure

- **Boot correctness.** Smoke is the source of truth.
- **Driver dependency on HAL exports.** Anyone importing from `hal.dll` (PnP managers, ACPI driver, video drivers) needs the ABI to stay stable. `hal.spec` is the contract.
- **Real ACPI on arm64.** The bindgen ACPI tables work for that future, but the rest of the arm64 HAL surface (GIC programming, generic timer) is net-new and not in scope.

## Open questions

- **Cohabitation vs. full cargo cdylib.** Cohabitation works today and avoids a flag-day cutover. The cdylib path is still possible later but no longer urgent.
- **HAL-into-ntoskrnl merge.** Drops the DLL boundary entirely (one `kernel-rust` blob, one LTO unit). Not blocking; revisit after Rust HAL is stable. FreeLDR's `winldr.c:719` hardcodes `"hal.dll"`; merge requires loader path changes.
- **`bios.c` setjmp/longjmp story.** Recommendation stands: keep as C, call from Rust through extern surface. Forcing this through Rust buys nothing.
- **Portable-submodule trait extraction.** Original plan had `irql/`, `acpi/`, `bus/`, `arbiter/` as portable submodules taking arch backends as traits. Hasn't been needed yet — the x86 arch split inside files is sufficient. Revisit when (if) arm64 grows a real Rust HAL.
