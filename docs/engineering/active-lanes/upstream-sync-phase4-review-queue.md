# Phase 4 review queue — 194 flipped TUs whose dead C the merge just refreshed

Generated by the upstream-sync lane at merge time. **This is the payoff of the
reframe**: each `.c` below is commented out in CMake and owned by a Rust twin, so
merging upstream's changes into it could not break the build — and it turned each
one from archaeology into an ordinary diff against text already in our tree.

Read one with:

```bash
git diff <the merge commit>^ <the merge commit> -- <c_path>
# ...then read the .rs beside it
```

Ordered by churn within each crate; the churn is a rough proxy for how much upstream
changed, not for how likely a bug is.

## The merge made two latent stubs REACHABLE — fixed at the point of hazard

Both are the same shape and both are worth internalising: **a stub that was harmless while
nothing called it becomes a bug the moment the merge brings in a caller.** Neither showed up
as a conflict, a build failure, or a smoke failure.

**1. `INetCfgComponentPrivate_fnUnknown1` returned success without writing its out-pointer.**

The merge changed `sdk/include/reactos/netcfgx_undoc.h`:

```c
-    STDMETHOD_(HRESULT,Unknown1)(THIS_ DWORD dwParam1, DWORD dwParam2) PURE;
+    STDMETHOD_(HRESULT,Unknown1)(THIS_ REFIID riid, void **ppv) PURE;
```

...and brought in `dll/win32/ifmon/ip.c` (+2409 lines of new `netsh interface ip`), which does:

```c
hr = INetCfgComponentPrivate_Unknown1(p, &IID_ITcpipProperties, (PVOID*)&pTcpipProperties);
if (hr != S_OK) { DPRINT1("...failed\n"); goto exit; }
hr = ITcpipProperties_Unknown1(pTcpipProperties, InterfaceGuid, &pInfo);   /* <-- */
```

Our Rust twin was translated from the pre-merge header, took two `DWORD`s, and **returned
`S_OK` without touching `ppv`**. The caller's own error check passes, and it dereferences an
uninitialized stack pointer. Fixed: correct signature, `*ppv = NULL`, `E_NOTIMPL` — so the
caller takes the failure path it already has. The real body (upstream's `CreateNotifyObject`
+ delegate to `pItem->pControl`) needs `CreateNotifyObject` and the `pItem`/`pControl` fields,
none of which exist in `netcfgx-rust` yet. **That port is still owed.**

**2. `SetSearchPathMode` is now settable but is not enforced.** `kernel32-rust` gained the
export (validation and the permanent-flag lock are faithful, and match the apitest), but our
`BasepComputeProcessPath` was translated from the pre-merge C and does not read the flag —
upstream's does, including a registry read of the safe-search-mode value. So safe DLL search
order can be requested and is silently ignored. **Security-relevant; owed.**


## Leads the LINT sweep produced for free

`verify_translation_literals` turned out to be an oracle in its own right. It compares the
literals in a translated `.rs` against the `.c` it came from — so the moment the merge
refreshed the dead C, every literal upstream had changed lit up. All 77 findings traced to a
real upstream commit; the four below are the ones where upstream changed *behaviour*, not
just text, and our Rust still carries the old version.

| Lead | What upstream did | Why it matters |
|---|---|---|
| `syssetup/wizard.rs` — keyboard layout | `d482579dff3` "Fix retrieval of the currently active keyboard layout ID and its name (#9420)" | Our Rust still has the **pre-fix** logic. Named as a fix by upstream, so this is the classic oracle shape. |
| `syssetup/wizard.rs` + `install.rs` — Gecko | `a4b6fe9630e` revamped the Finish page and **removed the Gecko installer**, replacing `appwiz.cpl,,install_gecko` with `RappsDownload` | Our Rust still invokes the old path on an unattended finish. |
| `syssetup/install.rs` — TCP/IP at setup | New block installs and starts `MS_TCPIP` / `Tcpip` / `Dhcp` / `Dnscache` during `InstallReactOS()` | **We do not do this at all.** A missing setup step, not a wrong one. |
| `umpnpmgr/umpnpmgr.rs` — MiniNT detection | `b1bd421163b` replaced parsing `SystemStartOptions` for `MININT` with testing for the `SYSTEM\CurrentControlSet\Control\MiniNT` key (`g_IsLiveMedium` → `g_IsMiniNT`) | A redesign, not a fix — worth deciding which detection is actually robust before porting. |

Two more that are new capability rather than bug leads, recorded so nobody re-derives them:
upstream rewrote the netcfgx TCP/IP notify object (`9b450d9f7f7`, `c04c092a3e6`, `4369126acc8` —
registry-backed property pages) and implemented `INetCfgComponentControl::ApplyPnpChanges`
(`bd363a821e9`), which was a `FIXME` no-op at our fork point.

All seven files behind those 77 findings are cohab-flipped, so none of this affects the build.
That is the point: the C is inert, the diff is free to read, and the Rust beside it is the
thing to fix.


## Top 40 by churn, with what upstream actually did

Read this table first. The commit subjects are the triage signal; the churn is not.
A few headline items:

- **`ntoskrnl/ps/job.c` (+2198/−536)** — upstream *implemented job objects*
  (`55563444377` Create/Open/Assign/Remove/Terminate/Delete, `b272427baa3` UI restrictions).
  Ours are stubs; this is why `PspCloseJob` is absent from `ps-rust` entirely. This is a
  semantic port of a whole feature, not a bug fix, and the 2,198 lines of working C are now
  sitting in our tree as dead text ready to translate.

  The TCP/IP property sheets were largely unimplemented at the fork point and upstream has
  filled them in. Matches the netcfgx findings already queued from the subject-only triage.

  into a shared `ke/x86x64/cpuinfo.c`. We declined the new TU (both `cpu.c` are Rust here);
  the *logic* changes are still worth reading against the Rust.
- **`ntoskrnl/fsrtl/name.c` (+0/−314)** — upstream deleted their whole implementation in favour
  of `RtlIsNameInExpression`. If our Rust still carries the 314 lines, it carries whatever
  was wrong with them.

## Next up: `sdk/lib/rtl/rangelist.c` — and the reason it is first

The merge rewrote it (+357/-153) **and shipped a 371-line kmtest for it**
(`modules/rostests/kmtests/rtl/RtlRangeList.c`). A flipped file with a brand-new upstream test
is the cheapest possible port: the oracle arrives with the work.

It already caught a live bug on its first run — `RtlRangeList: pass=239 fail=1`,
`[1] Flags = 0x0, expected 0x1`. `rtl-rangelist/src/lib.rs` hand-wrote
`RTL_RANGE_LIST_ADD_SHARED` as `0x1`, which is actually `RTL_RANGE_LIST_ADD_IF_CONFLICT`
(`sdk/include/ndk/rtltypes.h`), so `RtlAddRange` never set `RTL_RANGE_SHARED` on the stored
entry and `RtlIsRangeAvailable` never saw a shared range. Fixed, along with
`RtlIsRangeAvailable` testing the entry-flag constant where it meant `RTL_RANGE_LIST_SHARED_OK`
(same value, wrong namespace — it worked by coincidence). This is the class `--seal-facts`
exists to prevent, in a crate that predates it.

Also fixed, from the header type sweep: upstream widened `RtlFindRange`'s `Length` and
`Alignment` `ULONG -> ULONGLONG`, and the merge's `ntoskrnl.spec` update
(`ptr int64 int64 int64 int64 long long ptr ptr ptr`) had been reverted during conflict
resolution while the Rust callee stayed 32-bit. The real C caller is the PnP resource arbiter
(`sdk/lib/drivers/arbiter/range.c:762`), so on i386 that was an 8-byte stdcall callee-pops
mismatch per call. Caught instantly by the decoration checker once the callee was widened —
`undefined symbol: _RtlFindRange@48` — which is the field manual's "stdcall decoration is a
free ABI width checker" earning its keep.

### The port itself — DONE, by hand

Hand-ported rather than paid: `rustconv translate` would have re-bought a file that already
has output (which needs approval anyway), and this is plain list-walking C with a
240-assertion oracle sitting next to it. What changed:

- **Three new private helpers.** `RtlpOverlaps`, `RtlpWindowIsAvailable` (the shared
  availability walk now behind both `RtlIsRangeAvailable` and `RtlFindRange`, reporting the
  *lowest* conflicting Start so a top-down search can jump past it) and `RtlpConflictsOnAdd`.
- **`RtlAddRange` had no conflict detection at all** — every add succeeded. It now rejects an
  overlapping incompatible entry with `STATUS_RANGE_LIST_CONFLICT` unless the caller passed
  `RTL_RANGE_LIST_ADD_IF_CONFLICT`. Its insertion point also compared the new entry's **End**
  against the cursor's Start; the list is sorted by **Start**.
- **`RtlFindRange` is a different algorithm.** It was a single-shot "round down from the
  highest entry and hope"; it is now a top-down search that re-probes, jumping the window
  below the lowest conflicting entry each round (which strictly decreases the candidate, so it
  terminates).
- **`RtlInvertRangeList` was only correct for a non-overlapping list.** It walked adjacent
  pairs and emitted the gap between them — but `RTL_RANGE_LIST_ADD_IF_CONFLICT` permits
  overlaps, and an absorbed entry then produced a bogus inverted range. It now delegates to the
  new `RtlInvertRangeListEx`, which walks the covered space upward, absorbing every range that
  covers the cursor before looking for the next gap.
- **`RtlGetLastRange` and `RtlInvertRangeListEx`** are implemented, and their `ntoskrnl.spec`
  lines (reverted during conflict resolution) restored with them — implementation first, spec
  second, which is the order this lane learned the hard way ~230 times.
- **Deleted the crate's `ROUND_DOWN` helper.** It rounded through `usize`, modelling a
  `ULONG_PTR` cast the C expression does not have, so on i386 it truncated a 64-bit candidate
  to 32 bits. `RtlFindRange` was its only caller and now does the arithmetic in `ULONGLONG`.
